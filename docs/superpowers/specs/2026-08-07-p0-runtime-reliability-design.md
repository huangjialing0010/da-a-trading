# P0 运行可靠性收口设计

日期：2026-08-07  
状态：已实施。

## 目标

在不改变策略参数、订单数量规则、账户状态和趋势 V2 验证口径的前提下，收口首次受控日更暴露的三个运行问题：Windows GBK 控制台可能在末尾打印失败、日报错误承诺自动启动 AI 研究、深价自动订单缺少稳定的语义幂等边界。

本次不运行活动账户日更、不修改现有订单、不连接券商、不推送远端。

## 一、控制台输出兼容

报告文件继续以完整 UTF-8 保存，不删除 emoji 或中文。CLI 启动时保留当前标准输出编码，只把编码器的错误处理改为 `replace`；GBK 无法表示的字符可以显示为替代符，但不得抛出 `UnicodeEncodeError` 中断命令。

兼容逻辑放在 CLI 输出边界，不进入报告生成、账户写入或交易模块。无法调整输出流时保持原行为并输出最小 ASCII 告警，不得影响日更主体。

## 二、研究队列文案

日报末尾改为：已生成待研究候选队列，需要独立 AI 或人工研究任务处理。明确 GitHub Actions 不调用大模型，也不会自动创建研究文件。

本次只修正文案，不实现研究任务调度，不创建自动化，不改变候选、研究结论或订单。

## 三、订单语义幂等

### 趋势 V2

保持现有整批锁：同一仓、同一信号日、同一方向一旦形成买入批次，当日重跑不得扩充新标的。终结订单也保留批次存在性，避免取消后重跑重新选股。

### 深价仓

深价仓不能使用整日全锁，因为同日可能合法产生多个分批加仓、多个恐慌 ETF 订单以及卖出风控。新增稳定语义键：

```text
warehouse + signal_trade_date + direction + code + kind + batch_number
```

- `kind` 来自订单 metadata，例如 `batch_add`、`panic_initial`、`panic_add`、`panic_exit`。
- `batch_number` 仅用于有批次的订单；没有批次时使用空值。
- 同一语义键无论历史订单处于 `PENDING`、`BLOCKED`、`FILLED` 或 `CANCELED`，都不得再次创建。
- 不同股票、不同订单类型或不同批次号互不阻塞。
- 买入语义锁不得阻止卖出、止损、恐慌退出或其他降低风险的订单。

订单历史不删除。兼容既有账本：缺少 metadata 字段时按空字典处理；不迁移旧订单文件，不改写已有订单 ID。

## 四、组件边界

- `main.py`：配置控制台错误处理。
- `tools/auto_trader.py`：修正研究队列文案，并给深价自动订单提供稳定语义字段。
- `tools/paper_orders.py`：提供只读语义意图查询；不扫描候选、不决定策略。
- `tests/`：使用临时订单账本和模拟输出流验证，不触碰活动账户。

## 五、测试与验收

至少覆盖：

1. CP936/GBK 严格输出遇到 emoji 时命令不抛异常，中文可继续输出。
2. UTF-8 输出仍保留完整字符。
3. 日报不再出现“CC 将自动启动深度分析”。
4. 同一深价股票、订单类型和批次号重跑只创建一次。
5. 同一股票的不同批次可以分别创建。
6. 同日不同股票的恐慌初始订单可以分别创建。
7. 同日买入锁不阻止卖出订单。
8. 已取消的语义意图重跑也不得复活。
9. 趋势整批锁现有测试继续通过。
10. 全量测试零失败，不运行 `main.py daily`。

## 六、风险与代价

- GBK 控制台中的 emoji 会显示为替代符，终端观感下降；Markdown 报告不受影响。
- 语义键定义错误可能误拦合法深价订单，因此按股票、类型和批次细分，不采用整仓全锁。
- 已取消的同日意图不能自动重建；若确需重发，必须等下一交易日形成新信号，牺牲机会换取可复现性。
- 本设计只提高运行和审计可靠性，不提高收益，也不保证盈利。
